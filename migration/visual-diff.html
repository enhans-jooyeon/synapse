Three structural changes. Renamed in the same release: fg-* → text-* (matching Atlassian/Carbon/Polaris), the five "for use on inverted" tokens → -on-inverse, and radius-10 → radius-control-md. Compound <family>-fg tokens (action-primary-fg, ai-fg) deliberately keep -fg: there it means "the foreground paired with this fill", Material's onPrimary concept, not a position on the text scale. Icons keep a dedicated family, matching Atlassian, Carbon and Polaris (Material 3 is the outlier that unifies them). But only icon-primary carries its own value — one ramp step lighter than text-primary, because a stroke icon reads heavier than a glyph at equal value. The other 8 alias fg-*/status-*, so the API exists without the old system's hand-maintained 80% duplication. Borders drop numeric steps and paired hovers for named weights, encoding hover by ladder position (default → strong) rather than a suffix. Surface hovers became alpha overlays that composite over any fill, which is why the old system needed a solid hover per surface and the new one needs two overlays total.

The count grew 70 → 104. The growth is in families the old system had no equivalent for: action-* (20), icon-* (9), ai-* (5), glass-* (7), emphasis-* (4), viz-* (8). Old button colours lived in a flat button-* family of 18; those became action-*.

icon + text both at text-primary icon at icon-primary, text at text-primary

Status went from 2 roles to 4. Old had only error and success — no info or warning at the semantic layer. Each new role carries three renderings (deepened text, pale tint, mid solid), so old text-error #e6483d splits: the deepened status-danger #B23230 for text, and status-danger-bg-solid #DB504D keeps the old brighter value for fills.

Retired: category-1…8-bg / -text (16 tokens) plus the purple/teal/magenta ramps that only existed to feed them (33 primitive steps). Avatars, taxonomy Badges/Chips and calendar dots now take bg-sunken + text-secondary.

Why. The hue was assigned by hashing a label, so category-5 meant "hash slot 5" — no meaning, and an undocumented stability contract: changing the hash, the slot count or a label would silently recolour every existing tag. Against §1.1's rule that colour is a scarce resource spent only on meaning, an arbitrary hash hue is decoration. Identity reads from shape (squared avatar = agent, round = human) and the label, which were always the load-bearing channels.

Why the fill went away. The old field read as a filled surface (bg-background-100), which put it in the same visual class as a Card. Borders-first means the field is defined by its perimeter, so the fill is now bg.page and the border carries the state. Consequence for the codemod: bg-background-100 is a two-target row — Cards → bg.surface, inputs → white + outline. It cannot be a single find-replace.

Focus is the one place entry surfaces deviate. Non-entry controls take the 2px indigo border.focus ring offset 2px; entry surfaces do not — they swap to the neutral border.focus-input perimeter, because a text field shows focus on every click-to-type and the caret + border swap already form a compound indicator (foundations §1). So the old brand-blue focus border does not map to the new blue ring; it maps to a neutral. Any codemod that sends border-border-brand → border.focus is wrong on fields.

opacity-50 cannot be swapped for a token. Opacity multiplies through every descendant — label, icon, caret, helper text — so the old disabled treatment is not expressible as a colour. Each component applies its own disabled recipe instead (bg.disabled + text.disabled + border.subtle). This is a rewrite, not a remap, and it is one of the three unknown site counts blocking the sprint estimate.

Notifications

Two shape rules replaced two props. indicatorType="check" (8 sites) and labelPosition="left" (10 sites) both go away, because the shape and the label side now carry meaning rather than being author choices: circle+dot = exactly one, box+check = many, and the label is always right. The check variant was requested again on 2026-07-31 and declined — not because a circle+check loses the single-vs-multi signal (it does not; the silhouette still reads as a circle) but because it would make two renderings legal for one state, and because a check inside a 16px radio's ~8px interior sits below the 12px icon floor. It also expresses nothing the dot does not. Converting the 8 sites is mechanical. A far-apart settings row changes the layout (a DescriptionList row), not the label side. Note the key colour is black, not the old brand blue — selection is a neutral state, and azure is reserved for brand/AI emphasis.

One token became two, because one value cannot do both jobs. The old #10b978 / #e6483d were used as label colour and as solid fill. As text on white they run below AA, so the new system deepens the text tokens (#0E7A42, #B23230) and keeps a separate mid-tone for fills. Codemod consequence: every old status colour is a two-target row — text usages take the deepened value, fill usages take *-bg-solid. A single find-replace will either break contrast on labels or wash out fills.

Danger also left the solid-label deviation (2026-07-30). status.danger-bg-solid moved red.400 → red.500 #D2403E so a white label clears AA at 4.62:1 at normal weight — the semibold mandate on destructive Button labels is withdrawn. Old #e6483d → #D2403E is now a closer match than before (ΔE 30.5 vs 35.0). success and warning solids remain in the §9 deviation at ~3.5:1 with semibold compensation.

The new system is strictly richer here — nothing is lost. Old Alert had two variants; new Banner/Alert has five colours × two emphases. The visible change is that subtle notices are borderless: a status.*-bg tint with status.* text, no border and no rail. Tint plus a saturated outline is the forbidden "wireframe formula" — which is exactly what the old destructive alert was. This is also why border-border-success has no new equivalent: success surfaces are borderless by design, and border.error exists only as a form-field validation perimeter. A principled asymmetry, not an oversight.

Tooltip — the arrow is gone (77 sites)

Old

New

Ruled 2026-07-30: no floating surface in the system has an arrow — not Tooltip, not Popover, not Menu, not HoverCard. So TooltipArrow / tip / tipPosition are dropped with no replacement across 77 sites, the largest pure-deletion in the migration. Mechanical, but it needs announcing: the arrow is the thing that visually binds a tooltip to its trigger, and its absence is carried instead by proximity and the 4px offset. Tooltip size (sm/md/lg) also squashes to one size — listed under "squash without further thought". The other change is the surface, and it is easy to miss: the old tooltip was a dark inverse chip; the new one is same-scheme (bg.raised-2 + 1px border.default + text.primary, radius xs) — light in light mode, dark in dark mode, because "inverse surfaces read too stark against the neutral field". Inverse/contrast-flipped tooltip styling is now explicitly forbidden, so a codemod that preserves the old dark chip is carrying over a retired treatment.

Toast — a visual component, not a queue

Old

imperative toast() + <Toaster>

Filter saved

New

Toast surface + Undo convention; queue is app-owned

This one is an engineering decision, not a design mapping. The spec describes a Toast queue (max 3, auto-dismiss 5s, errors 8s) but the built package does not export an imperative API — so either the library ships toast() or the app owns the queue. One site today, so it is cheap to decide either way, but it should be decided rather than discovered. The design-side addition is the Undo convention: reversible-lite mutations confirm via Toast with an Undo action at 8s instead of pre-confirming, so a Popconfirm and an Undo Toast never both appear for one action.

The split is deliberate and it resolves a real ambiguity. Old segmented becomes the separate SegmentedControl component, because the two do different jobs: Tabs switch peer views of one object (and are navigation), SegmentedControl switches a parameter with immediate effect (1D/7D/30D, list/grid). Having both as "tab variants" is what let engineers pick by appearance rather than by meaning. Open decision: old fill tabs have no equivalent at all — confirm they are not needed rather than discovering it mid-migration. Also note the active indicator moved from brand blue to a neutral 2px bg.inverse underline, consistent with "the primary action colour is black, not blue"; the old blue-underlined tab is a treatment to retire, not to remap.

DynamicTabs → Tabs variant="editable" (16 sites, mechanical). Added to v1 on 2026-07-30 specifically to close this migration gap: trailing 12px ✕ per tab, a + button parked outside the scroll region, double-click to rename in place, and closing the active tab activates its right neighbour. The 7-tab cap is enforced differently here — author-defined tabs are capped by review, but user-created tabs can't be, so the + disables at 7 with a Tooltip rather than allowing an unbounded scrolling strip. A surface that genuinely needs 30 open items is a Sidebar list or a Tree, not a tab strip. Separately, shadcn's icon-only triggers go to icon + label: an icon alone cannot carry a user-named view.

Stepper — the one genuine gap in this section

Old

1 2 3

New

This is a real absence, not a deliberate squash — and it is the only one in this section. The inventory diff states it plainly: the new system has Timeline and the guided archetype but no Stepper, and "a guided flow arguably needs one." The two candidates do not substitute: Timeline is chronological and read-only (audit trails, run history) whereas a stepper is positional and forward-looking — it says "you are on 2 of 4" before the later steps have happened. Tabs are explicitly forbidden as a stand-in ("Tabs are object facets, not sequential steps — compose a stepper"), which names a component that does not exist. Decision needed before any guided flow ships: add a Stepper via §6 governance, or rule that guided flows carry progress some other way and correct the Tabs prose that currently points at it.
